## 修复行为

- 仅新增聊天专用回执组件`public/chat-delivery.js`，不改建房、牌局行动、资金、重连身份或聊天服务端处理。
- 每次发送最多等**8秒**。收到`ok:true`才显示“已确认发送”；明确`ok:false`显示“未发送：原因”；超时、无效回执或发送中断线显示“送达状态未确认”，不把超时说成服务端一定没收到。
- 输入框保持可编辑；成功回执只有在原输入值和编辑版本均未变化时才清空。先修改、再改回相同文本也不会被旧回执清掉。
- 发送中只允许一个请求。超时/拒绝/断线的原文保留在可展开、可滚动的“发送记录”中；当前输入里的后续草稿也保留。原文可手动重发，重发原文不会覆盖另一个当前草稿。
- 未确认的相同原文（按服务端同口径规范化比较）不能从主按钮直接重复发送；需先核对聊天记录，再使用明确标注的重发入口。**没有自动重发。**
- 只有传输已连接且房间状态已恢复才允许发送；使用Socket.IO的限时、volatile发送，断线结束本次等待，不把聊天作为普通离线消息无提示排队。旧请求、跨房间请求或已过期请求的回执不能改当前请求UI。
- 沿用原有聊天限频、80字符限制、服务端规范化/验证与转义。待处理原文使用`textContent`渲染。提示使用原有聊天区域，没有新增覆盖牌桌的大弹窗。

## 隔离方法与复现入口

运行`node test/chat-ui-fixture.js`，浏览器打开输出的本机随机端口，创建一个测试房并打开聊天。只有测试浏览器连接，无真实玩家。使用真实服务端聊天处理，夹具只控制聊天回执或这一隔离连接：

- `normal`：真实正常回执。
- `hold` / `release`：服务端照常处理消息，暂扣/按顺序释放一个回执。
- `lost`：消息已处理、回执永不返回；不等同于消息未送达。
- `blackhole`：不调用真实聊天处理、也无回执，用于模拟请求未到达。
- `offline` / `online`：真实关闭测试连接，暂拒/恢复该隔离服务握手，不改用户网络。
- `release-previous`：每次新请求到达，先释放上一条旧回执，暂扣当前回执；可稳定复现旧/新请求交错。
- `delay`：正常处理后延迟1500ms回执，便于再次核对短延迟成功。
- `status`：只读测试房聊天记录。

先后使用本机64331、65041端口。截图昵称、文本和房间均为本轮虚构测试内容。未停止或刷新用户试玩页、3000/3477/3478、旧d260或隧道。临时页面、两个隔离服务均已关闭。
