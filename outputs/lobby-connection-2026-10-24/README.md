# 大厅连接反馈：只读诊断

2026-10-24；基线`bcce684`。只新增本地故障夹具及证据，**业务文件未改、未发布**。结论仅保留下面两个已稳定复现的问题。

## 1. 首次实时连接失败没有反馈，离线提交会在恢复后执行旧请求

**实际证据**

- [01：375大厅](01-A-first-connection-failed-no-feedback.jpg)：静态页与脚本已加载，实时连接握手持续被夹具拒绝；没有连接失败/未连接提示，“创建房间”“加入”仍可用。
- 提交一次“初连创建”、起始筹码2340后，[02](02-A-offline-create-remains-busy.jpg)一直显示“正在创建”，输入、返回和其他大厅入口被锁定，无其他状态。标记已提交后又等28.3秒才恢复连接，期间服务端没有收到建房请求。
- 不再点击建房，只恢复测试连接。恢复后26毫秒，服务端收到原来的`create_room`并建出QTPCHK；[03](03-A-recovery-executes-old-create.jpg)自动进入该房间。
- 568低高度查房对照：[04](04-A-offline-query-remains-busy-568.jpg)昵称和邀请码被锁住，显示“查询中”。恢复后原来的`room_info`自动执行，[05](05-A-query-recovery-opens-preview.jpg)打开说明预览；没有第二次点击，也没有实际加入房间。

**用户影响**：用户无法分清“还没连接”“正在处理”与“失败”；不能编辑或退出当前提交。之前点击的建房会在较晚恢复时发生，而页面没有说明它已经被留待发送。

**代码关联**：`public/client.js`的`beginLobbySubmission`（311行）在提交前不检查连接；创建、查房直接使用普通`socket.emit`（349、387行）。没有首次`connect_error`的大厅反馈。首次成功连接分支直接返回（709行附近），此前提交仍由Socket.IO缓冲后发出。结论由当前请求时间线确认，不只凭代码推测。

**最小安全改法（建议，未实施）**：只在大厅增加清楚的连接状态及提交前守卫。未连通时不创建待发送业务请求、不进入无限忙碌态，保留表单；恢复后提示可继续，让用户主动提交。不要顺带改牌局行动队列或全站请求协议。

**验收标准**：静态页可用而首次握手失败时，375/568都有可见状态，表单可保留/编辑；没有离线`create_room/room_info/join_room`排队。恢复后、再次明确提交前，服务端请求计数不增加；一次主动提交只执行一次。

## 2. 已连接后丢回执会无限等待；创建结果未知时“请重新提交”可引导重复建房

回执指服务端对这一次请求的答复。**丢回执不等于请求没有成功。**

**实际证据**

- 查询对照：服务端已成功处理`room_info`、夹具仅丢回执。30.1秒后仍为[06：查询中](06-B-connected-query-lost-ack-568.jpg)。真实断线后，[07](07-B-query-disconnect-unlocks-keeps-draft.jpg)解锁，并保留昵称和房号，提示“连接中断，请重新提交”。恢复连接后没有自动重查，这是本次观察到的正常边界。
- 创建主案例：服务端已建出**F88Z3G**，并发送包含该房号/本人席位的状态广播，只有创建回执被丢弃。37.9秒后，[08](08-B-create-ack-lost-still-busy.jpg)仍锁在“正在创建”，没有显示房号或结果未确认提示。该次DOM记录为大厅可见、游戏隐藏、房号显示为空。
- 随后只断开该测试连接。[09](09-B-create-disconnect-says-resubmit.jpg)恢复了操作和原草稿（“回执丢失”、2460），但提示仍是“连接中断，请重新提交”，没有说明原房可能已经成功创建。
- 重连后没有自动回到F88Z3G。按当前提示手动再点一次建房，服务端又建出**DUK3H8**，[10](10-B-manual-retry-creates-different-room.jpg)进入新房。最终服务端记录显示F88Z3G和DUK3H8同时存在，均为同一测试昵称；原房不是“未建成”。

**用户影响**：轻则大厅长期不可操作，重则把原本应核对的创建结果当作失败，再建另一个房间，丢失对原房身份/邀请目标的判断。此处没有证明资金变化或权限绕过，也不作这种声称。

**代码关联**：大厅忙碌态没有有限回执等待；保存新房凭证和进入房间只在创建成功回调执行（349–355行）。大厅断线分支统一`endLobbySubmission()`并提示重新提交（722行附近），没有按只读查询与创建操作区分结果未知的含义。夹具没有修改业务处理、状态广播或重连token规则。

**最小安全改法（建议，未实施）**

- 对已发送请求增加有限等待、保留原表单并显示准确状态。查询是只读操作，可提供明确的手动重查；创建/加入超时或断线则显示“结果未确认”，不能当作确定失败，也不能定时自动重发。
- 创建未知态先阻止误导式“一键再提交”，提供核对已知房号/现有结果、返回编辑等安全选择。若要新建另一个房间，应明确是新操作，不冒充重试原操作。
- 已收到房间状态也不等于已拿到创建回执中的重连凭证。原房的身份/凭证核对路径需要负责人另行选定；**不建议仅靠昵称、旧last-room或公开房号恢复身份，不绕过token**。本次不擅自设计请求ID、幂等协议或新的恢复接口。

**验收标准**：已执行但丢回执的创建进入明确“未确认”状态，保留资料，不自动重建；断线/恢复不直接引导用户再建。服务端已有房间时，普通恢复流程不得悄悄增加第二个房间。只读查询有限等待后可手动重查且保留昵称/房号。具体原房恢复路线未定案前，不宣称只改提示就已经解决身份恢复。

## 过程步骤与健康状态

1. **首次连接失败——需改进**：HTTP正常、握手失败，无大厅连接反馈，首次离线提交在恢复后执行。
2. **已连接查询丢回执——需改进**：等待没有上限；真实断线后解锁和保留草稿正常，恢复后没有自动重复查询。
3. **已连接创建丢回执——需优先改进**：已成功创建却仍忙碌，断线提示引导再提交，重连后明确复现第二个房间。
4. **草稿与身份边界——部分正常**：断线保留昵称、房号/筹码设置；未观察到跨token恢复身份。原创建回执丢失时，没有成功完成原房的正常进入/凭证确认。

## 与Render普通冷启动的区别

本轮**没有测试或判断Render线上冷启动**。静态页/脚本在A中正常返回200或304，只故意拒绝本机测试实时握手；B中服务端已经处理完成并产生结果，只丢请求回执。因此不能用“服务还未启动”解释B中的等待。

正常冷启动可以暂时需要等待；应准确告知连接阶段。本报告的问题是缺少阶段反馈、请求被无提示留待恢复执行，以及把创建未知结果引导成重提；不是把所有等待或所有延迟执行都认定为错误，也不推断线上发生频率。
